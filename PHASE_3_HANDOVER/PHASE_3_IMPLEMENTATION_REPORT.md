# Phase 3 implementation report

28 October 2026. This phase adds automatic discovery to a separate copy of the existing WPF/PDFium prototype. The Phase 1 and Phase 2 handovers were reviewed before implementation. Phase 2's interface, native RichTextBox, debouncing, revision handling, draft preservation and verified Save As remain the foundation. The earlier build and evidence are retained unchanged.

## Delivered behaviour

An ordinary digital PDF without `.region.json` can now expose supported text regions. The supplied letter and report were generated by ReportLab; another supported letter was generated independently by MuPDF. Existing controlled samples retain their manifest validation path. A present but invalid manifest fails closed; discovery does not bypass it.

Launch `../phase3/run/PdfEditorPrototype.exe` or `../phase3/Launch.ps1`. The default document is the manifestless `01-letter.pdf`. The delivered Windows x64 build requires .NET 8 Windows Desktop Runtime; it was built and exercised on this machine with that runtime installed. No installer or validated self-contained distribution is supplied.

## Changes and boundaries

`phase3/Core/Discovery.cs` analyses the requested page in the worker. It observes top-level object indices and bounds, text-object strings, character-to-object mappings, glyph bounds/origins, matrices, baselines, font size, opaque colour, embedded font bytes/hash and WPF font face/style/metrics. `DocumentInfo.PageObjects` also exposes neighbouring path/image/form boundaries. Nested form contents are conservatively unsupported rather than recursively claimed as owned text. Font identity is based on the original program hash and object linkage, not a promise to preserve resource dictionary names.

Visual ordering uses baseline and horizontal position, independently of content extraction order. A complete text object is the candidate line unit. Fragmented lines, same-baseline competing blocks and uncertain short-line relationships are restricted. Paragraph joins require matching left edge, font hash, size, colour, stable leading and a preceding line occupying at least 70% of the inferred width. Page margins and nearby objects bound the available area. These relationships and space are explicitly recorded as **inferences**, separately from observed properties. They are geometric rules, not recovered author intent or a confidence score.

The three states are Editable, Limited and View Only, with deterministic machine-readable reason arrays. Only Editable activates the existing inline editor. Clicks on unsupported text show a status message. No permanent outlines, diagnostic panels or replacement-text modal were added.

For automatically discovered regions, the original font is extracted into a session font folder keyed by hash. Each hash has its own directory because a WPF font-directory cache defect was reproduced when adding different files to an already scanned folder. The font program is not renamed, substituted or redistributed as a bundled font. The editor uses its actual family, weight and style. Original program hashes are checked again before selection/save.

Supported automatic edits currently require simple opaque fill text, identity-scale horizontal matrices, approximately natural glyph spacing, 6-48 pt fonts and ASCII U+0020-U+007E. A temporary text object probes the original PDF font encoding against the available font cmap; it is removed before rendering or saving. The current all-character probe is deliberately conservative: the Word and MuPDF subset examples fail it and remain view-only, even when a smaller proposed edit might be possible. This is not general subset expansion or Unicode support.

Local spacing tolerance is 0.05 pt, baseline tolerance 0.15 pt and cumulative origin discrepancy at most 1 pt. This permits small PDF metric rounding differences while rejecting explicit character spacing. It does not establish pixel-identical WPF/PDF typography. Paragraph leading is 1.05-1.65 times size with stable repeated spacing within 0.25 pt; separate single lines use 1.5 times size. Left edges must agree within 0.25 pt. These constants define a tested narrow class, not universal PDF rules.

## Integration and persistence

The original click/caret calculation, native selection/input/history, wrapping and draft verification remain. Multiple discovered regions are selectable. One changed region is committed per Save As. Switching directly to another region with an outstanding changed draft is refused with a message; save and reopen the result first. Opening another document/page preserves a recovery snapshot. Automatic recovery is keyed by source fingerprint and region ID; controlled-sample recovery retains its earlier key. Undo history remains per active opening.

The worker removes the complete owned text objects, creates replacement lines with the original font handle/style, generates PDF content, saves a temporary candidate, reopens it and verifies it. No covering rectangle is used. Verification retains the Phase 2 checks for object removal, exact extracted replacement lines, embedded font program/style, neighbour text/style/bounds, page count/dimensions, annotation counts, selected metadata and pixels outside the edit area. Untouched pages are also compared. The original file and any existing destination cannot be overwritten. Failed validation retains the entire draft.

An append to a rediscovered wrapped paragraph exposed an old verifier assumption: its original text contains observed line breaks while the user's appended draft may be unwrapped. The intentional-retention check now also compares the planned replacement lines. Exact replacement extraction and original-object removal checks remain. No whitespace-normalising acceptance was added. Consecutive spaces can still fail exact extraction and are retained as a known refusal.

## Reopening outputs

The tests save a three-line first-generation edit, rediscover it from actual PDF content without a sidecar, append a second edit, export again and rediscover the final paragraph. Independent extraction retains both markers and removes the initial target. The WPF control suite separately performs two saves through the actual window's shared export method. Each generation undergoes the normal verifier. Empty deletion naturally leaves no region to select afterward.

## Responsiveness and offline operation

Analysis is incremental by requested page, called asynchronously in the child process. Pointer-free discovery is cached by full SHA256 and page, capped at eight page entries; font-file hashes are rechecked. Normal page raster names include the fingerprint and can be reused. Requests remain serialised, with a 30-second timeout/restart and revision guards against stale results. There is no hard cancellation of a currently running native analysis; newer opens can wait behind it. No large-document performance or hostile-file claim is made.

The measured small-corpus discovery calls, including worker round trip and rendering, are recorded in the test results. Native worker isolation is not an OS security sandbox. Document processing uses no server or cloud. Development corpus/verification tools are separate from the distributable; no Python, MuPDF, ReportLab, Poppler or qpdf library was added to the application runtime.

Native PDFium remains pinned to 156.0.8076.0 with the earlier DLL hash and supplied dependency notices. The controlled Prototype Sans asset and its license are unchanged. No application license decision was made on the user's behalf. API declarations were checked against the [PDFium public editing header](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_edit.h).

Phase 3 stops here. OCR, full reflow, merge/split, signatures, forms, annotation editing, cloud features, installers and Phase 4 work were not added.
